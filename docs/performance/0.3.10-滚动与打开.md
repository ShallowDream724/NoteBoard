# 0.3.10：Markdown 打开、滚动与转换

## 已确认的原因

1. 导出 Worker 只为 Markdown 解析提供简化的 DOM/window，编辑器高亮调度器在模块加载时却调用 window.addEventListener。即使文档没有代码块，也会因导入失败而中止转换。
2. 大纲打开时，每批公式真实高度变化都会使全局标题几何失效。重建逐个调用 ProseMirror nodeDOM，后者从兄弟节点起点扫描；平铺文档可达 O(H×B)，再叠加全篇布局读取与排序。
3. 行内公式回收后变成空 inline-block，其基线从最后一行移动到底边。只保留宽高仍会改变正文行盒，重新进入视口时又反向变化。
4. 公式固定每帧挂载两项、最多准备三项，把 Atlas 全部 466 个公式的队列拖到六秒以上。邻近窗口反复回收已排版的 DOM，滚动中再创建和测量，造成页面高度变化与同步布局；低优先级取消还会反复冷启动 Worker。
5. 首次 Markdown 模块请求原来依赖欢迎页空闲任务；初始化先建立空编辑器，再在后续 React effect 填入全文。schema 校验与 setContent 还重复构造文档模型。
6. 多个 Markdown 管理器共享 Marked 单例，重复注册规则；列表 tokenizer 对普通段落也拆分剩余全文，公式与提示块规则重复前探全文。普通长文首次解析出现近似平方级工作。
7. 历史读取错过已有末端缓存，反复回放补丁；批量替换的历史起点对每一步重新反转映射，形成平方级开销。
8. 搜索导航重新扫描全文并生成全部高亮；正则表达式直接占用主线程。搜索观察器还必须随查询和编辑器会话清理，空查询不能产生滚动定位工作。

## 修复后的职责

- codeTokens 是无浏览器依赖的数据与 HTML 序列化模块。导出转换直接调用 Worker 内的纯高亮引擎，不加载编辑器调度器，也不再创建嵌套高亮 Worker。
- 大纲按顶层流块分组，缓存标题 DOM；滚动对当前组位置二分，组内按实际 Y 排序。上方公式变高只改变组的位置，不使整篇标题缓存失效；局部变化只重新测量所查询的多标题组。
- 公式 DOM 由每个编辑器的会话管理。较小文档（不超过 512 项且公式源码不超过 64 Ki 字符）后台准备全文；大文档按邻近视口准备。在约 64k 元素／1024 项驻留预算内保留已有预览，只有超预算才回收远处内容，回收保持宽、高和基线。邻近及正在编辑的内容允许超过此软预算，不能宣称整个编辑器有硬内存上限。
- 挂载和回收共用按节点数量、时间与优先级调度的队列。轻量邻近公式可以在滚动中提交，重型及后台提交等滚动停下；16 个准备槽中保留 4 个给前台。编辑源码框及切换选区不重建已有公式 DOM，隐藏编辑器暂停准备。
- Worker 按最多 16 项、8192 字符、8ms 软预算批量处理并逐项返回；两秒无进展才重启。取消立即隔离消费者和旧结果，不为一个过期请求销毁所有工作。单个公式不能抢占，空闲 Worker 与有界结果缓存仍会释放。
- 应用启动握手后，与设置 I/O 并行准备 Markdown 模块，不实例化编辑器。编辑内核直接以经过 schema 校验的正文创建；保留 TrailingNode 的结构规则和解析失败时的原文降级。首次协调器通知复用同一个不可变文档，不再整篇替换。
- 短于 150ms 的模块加载不显示状态页；超过时显示简短状态。没有最短显示时间，模块一旦就绪立即显示编辑器。
- Markdown 管理器各自持有解析器；列表先判断首行，块规则只前探当前段落。模式定位按不可变文档身份复用一份索引，历史直接命中当前物化结果。批量编辑起点反向访问每个 StepMap 一次，不扫描全文或创建映射前缀。
- 搜索匹配索引与当前高亮分离；视口高亮最多 2000 项，F3 仅移动当前项。无匹配时不安装滚动观察器；关闭搜索或切换编辑器清理旧会话。用户正则进入可取消、有超时的 Worker，不回退主线程。
- 单项导出排版只检查受影响块与祖先，不再重新测量全部正文。表格拆列成功后才保留所需原始结构。信息图首次邻近才解析，选区或菜单变化不重复解析。

## 同机测量

脚本及原始结果与最初测量使用相同 Edge、视口和 Atlas。以下为隔离编辑器及算法测量，不代表完整安装程序或磁盘 I/O 延迟。

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 466 个公式经实际 DOM 队列完成 | 6.18–6.57 秒 | 0.75–0.86 秒 |
| 8 个公式的一屏经实际 DOM 队列完成 | 约 71ms | 11.8–16.6ms |
| Atlas 就绪后约 3.3 秒连续往返滚动的布局次数 | 401–410 | 0 |
| 同段滚动的文档高度变化 | 增加 3262–3299px | 0 |
| 同段滚动的最长帧间隔 | 约 100ms | 17–33ms |
| Atlas 源码定位索引首次构建 | 119–177ms | 约 6ms |
| 178,888 字符／4000 段落索引首次构建 | 2.70–3.10 秒 | 约 35ms |

队列测量不把结果缓存命中当作公式计算。纯 KaTeX 计算的初次冷启动和热机结果见最初的《公式延迟实测》；本次主要消除排队空转、重复解析和重复浏览器布局。新增搜索代码的一次空查询滚动回归在复测中被发现并修复：同段脚本耗时从约 2.6 秒回到约 154–155ms。

另测首开后立即滚动、不等待全文公式就绪：两轮最长帧间隔均约 33ms，布局 65–78 次／200–236ms，已挂载 175–201 项；仍有首次排版造成的 2279–2909px 高度变化，其中一轮记录到 55ms 长任务。该结果与“就绪后布局为零”有不同前提，不能混为所有情况下零延迟。

## 成本与限制

普通大纲滚动为 O(log G) 次组位置读取；查询组内为 O(log K)，该组失效时才重测 K 个标题并排序。结构重建、新标题首次定位和隐藏组跳过仍有额外成本，不能把整条链描述为无条件对数复杂度。

源码读取、首次语法解析、模型与可见 DOM 创建仍有随内容规模增长的必要成本。首屏模块预备会提前承担一份 Markdown 模块内存，不创建后台文档或公式 Worker。单个 DOM 操作及浏览器后续布局不能抢占；每帧调度预算不等于硬帧率保证。

验证针对真实转换 Worker 入口、初始文档身份与安全降级、局部大纲几何、公式取消／复订阅／超时、占位基线、索引归属及批量编辑复杂度。只重测与本次发现直接相关的热点，没有重跑整套实机回归。PDF 正文排版变化仍需系统引擎生成完整 PDF；完整可编辑表格仍保留原生 DOM，这两点尚不能宣称已完成大规模虚拟化。
