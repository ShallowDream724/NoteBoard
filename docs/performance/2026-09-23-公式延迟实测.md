# 公式延迟实测（2026-09-23）

本次只测量，不据此宣称性能问题已经修复。公式生成、浏览器布局、调度等待分别记录；没有用公式结果缓存代替重新计算。

## 测量环境与范围

- 本机 Intel i7-11800H，16 逻辑线程，约 32 GiB 内存。
- Edge 153.0.4234.48，headless，1400 × 1000 CSS px，缩放 1，无 CPU 降速。
- 应用源码固定到已安装 0.3.9 对应的 `3c129ad`；使用本机现有依赖（KaTeX 0.16.47），以生产配置构建独立测量页。尚未安装的 0.3.10 修改不参与本次基准。
- 3 个独立浏览器上下文。下表是各轮中位数的范围，不是单次最好成绩。
- 公式生成直接调用 `renderMathMarkup`，绕过应用结果缓存；同一公式每次重新解析、排版并生成 HTML/MathML。DOM 测量每次清空容器、重新构建节点，再强制完成样式和布局。
- 热态指引擎、字体已加载。冷启动另列。浏览器布局数据来自独立测量页，不等同于 Windows 安装程序的端到端打开耗时，也不代表显示器已经实际显示了该帧。

## 结果

| 样本 | 公式生成 | DOM 构建与布局 | 样本说明 |
| --- | ---: | ---: | --- |
| 简单公式 | 0.055–0.065 ms | 1.20–1.57 ms | `E=mc^2`，35 个元素 |
| 嵌套矩阵 | 0.26–0.32 ms | 2.49–3.61 ms | Atlas M069，143 个元素 |
| 较长复杂公式 | 2.93–3.29 ms | 25.3–35.0 ms | 18 项带范数、上下标及指数分母的分式和，2642 个元素 |
| Atlas 一屏 | 0.56–0.84 ms | 5.77–10.07 ms | 连续 M024、M025，8 处公式，保留标题、源码示例和文字；内容高 890 px |
| Atlas 全部公式 | 45.9–51.3 ms | 268–388 ms | 466 处全部重新计算，28522 个元素 |

简单与嵌套公式每轮计算 200 次，长公式 50 次，一屏 50 次，全部公式 10 次。DOM 对应每轮 20、20、10、10、5 次。完整数据含 P95、最大值和每轮结果，保存在测量 JSON 中。

Atlas 为 230 处行内公式、236 处显示公式；按源码及显示模式去重后有 229 种。本次全部公式生成仍计算了 466 次，排除了 LaTeX 代码块及行内代码。

冷态单独结果：

- 动态加载公式引擎并首次计算简单公式：25.2–30.7 ms。
- 新建公式 worker 并首次取得简单公式结果：36.8–41.5 ms。
- 引擎载入后首次计算全部 Atlas 公式：102–143 ms。
- 首次构建全部公式 DOM：79–92 ms；首次布局：470–526 ms；等待所需字体及随后重新布局：594–648 ms。这是整批全部挂载的冷态实验。
- 字体已就绪时，将 Atlas 原有标题、文字、代码示例一起重建，完整静态文档 DOM 构建与布局为 893–967 ms。此项不包括 Markdown 解析、公式生成、Tiptap 或 React 初始化。

## 调度成本

对已安装版本的真实 `mathRendering` 和 `mathRenderQueue` 另做测量：

- 每次调用前清空公式缓存，逐项经过 worker 调度处理全部 466 处公式：677–829 ms。
- 正常分帧队列处理上述一屏 8 处公式：约 71 ms。
- 正常分帧队列处理全部 466 处公式并逐项插入 DOM：6.18–6.57 s。此项保留应用正常的相同任务合并和缓存行为，不能拿来充当“无缓存公式计算”成绩。
- 全部队列实验的帧间隔 P95 为 33.5–49.9 ms，最大值为 66.8–100.0 ms。

源码中的限制与测量相符：队列最多提前准备 3 项，每帧最多提交 2 项，并逐项等待 worker。单帧的约 3 ms 预算只包围 JS 提交循环，没有把浏览器随后发生的样式、布局和绘制成本计入其中。466 项即便完全不花计算时间，按 60 Hz 每帧两项，也至少需要约 3.9 秒完成分帧提交。

因此，“把全部公式算出来很快”得到数据支持；把这些结果交给当前逐项调度与 DOM 生命周期后，延迟被放大。单个较长公式生成仅约 3 ms，却需要约 25–35 ms 完成节点构建和布局，已经能独占超过一个 60 Hz 帧预算。整个屏幕的卡顿不能统一归因为 LaTeX 计算重。

`requestAnimationFrame` 的两帧等待仅用于留出绘制机会，原始 JSON 的 `endToNextPaintOpportunity` 不作为纯渲染 CPU 时间使用；本报告没有将其固定约 33 ms 的等待误算成每个公式的计算时间。

## 实际编辑器滚动对照

用同一 `3c129ad` 的 Tiptap 扩展、React NodeView 和原有样式装入完整 Atlas；不挂载应用侧栏、标签栏或原生外壳。文件操作接口以空实现隔离。每组重复两次，保持同一浏览器和视口。

对照组仅在临时源码副本中将公式的邻近可见性判断改成始终可见，等待全部 466 个公式完成再滚动。这是用来定位工作发生在哪里的实验，未作为产品修改，也没有将其成绩冒充首次渲染时间。

| 连续滚动实验（每帧 180 CSS px，前后各 100 步，约 3.3 秒） | 当前懒加载 | 全部预先排版且不回收 |
| --- | ---: | ---: |
| 滚动期间浏览器布局次数 | 401–410 | 0 |
| 浏览器布局总耗时 | 491–515 ms | 0 ms |
| 滚动期间文档高度变化 | +3262–3299 px | 0 px |
| 最大帧间隔 | 99.9–100 ms | 17.1–33.3 ms |
| 帧间隔 P95 | 16.8 ms | 16.8 ms |
| 滚动结束时保留的公式数 | 30 | 466 |

这组测量发现偶发长帧，而非每一帧都慢；只报告平均帧率或 P95 会掩盖它。另一个按全文比例快速跳滚的实验，懒加载版也出现约 1160 px 的文档高度变化，但没有稳定复现明显长帧，因此“滚动感觉顿一下”还包含内容位置变化。

预先完成公式的对照，滚动时虽然保留约 3.2 万个元素，却不再触发布局；原懒加载组只有约 6100 个元素，却发生约 400 次布局。数据支持优先检查滚动期间的公式挂载、回收、尺寸占位与调度方式，不能简单把卡顿归咎于公式数量或 KaTeX 算不动。

此实验未覆盖完整原生窗口的侧栏、菜单等开销，也没有测定每个原生绘制或 GPU 阶段；它能隔离公式及编辑器链路，不用于承诺安装版所有卡顿均已找全或消失。

## 复现

在仓库目录运行 `node scripts/measure-math-latency.mjs`。脚本从 Git 提取基线到 `.tmp/math-latency/baseline`，构建独立页面，使用本机 Edge，输出 `.tmp/math-latency/results.json`。不修改应用源文件，不安装软件。

滚动对照使用 `scripts/measure-math-editor.mjs`，单独记录编辑器内的帧间隔、浏览器布局时间、CPU profile，并与预先渲染全部公式、滚动期间不回收的诊断对照比较。诊断对照仅存在于 `.tmp` 副本，不是已实施的产品方案。

先运行 `node scripts/measure-math-editor.mjs` 获得快速跳滚数据，再运行 `node scripts/measure-math-editor.mjs --reuse-build --continuous` 获得连续滚动数据。结果分别写入 `.tmp/math-editor-measure/results.json` 与 `results-continuous.json`；对应 CPU profile 同目录保存。
